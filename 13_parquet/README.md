# Parquet Index-Free Search Tutorial

This tutorial demonstrates **index-free search** in Lucenia (0.12.0+): querying a
Parquet file **in place** — without first ingesting, indexing, or copying it into
Lucenia. You *mount* a `.parquet` file as a read-only index, and Lucenia serves
searches and aggregations by reading data pages directly from the file at query
time using a custom Lucene codec.

You'll mount the classic 32-row `mtcars` dataset, explore what the read-only view
can and can't do, and then **promote** it to a regular index with the standard
`_reindex` API to unlock the full query surface.

> **Experimental feature.** Index-free search is experimental in 0.12.0 and is not
> recommended for production. It's ideal for *pre-ingestion inspection* (validate a
> dataset with real queries before committing to indexing) and *occasional queries
> over cold/archival data* without standing up an ingest pipeline.

## What You'll Learn

- Mount a Parquet file as a read-only index with `PUT /_plugins/parquet/<index>`
- Read the inferred schema and understand how Parquet types map to Lucenia types
- Run the supported query surface: numeric range/term, numeric aggregations,
  keyword term/match, `exists`, and `GET` by `_id`
- Recognize the deliberate limitations (keyword aggregations, sorting, boolean
  columns, and all writes are unavailable on a mount) and *why* they exist
- Promote a mount to a full index with `_reindex` to remove those limitations

## Mount vs. Ingest at a Glance

| | Mount (index-free) | Ingest (`_reindex` / `_bulk`) |
|---|---|---|
| Data location | Stays in the Parquet file | Copied into Lucenia's own store |
| Writable | No — read-only view | Yes |
| Setup cost | Instant, no copy | Reads + indexes every row |
| Query surface | Narrow (see [Part 3](#part-3--limitations-of-a-mount)) | Full: sort, keyword aggs, points, etc. |
| Best for | Inspecting / occasional queries | Repeated production querying |
| In this tutorial | `mtcars` (mounted) | `mtcars_ingested` (promoted) |

## Prerequisites

- Docker and Docker Compose V2
- A valid Lucenia license file (`trial.crt`)
- `curl` (the tutorial scripts use it)
- Nothing else — the sample Parquet file is generated locally if you already
  have `python3` + `pyarrow`, and otherwise inside a throwaway
  `python:3.12-slim` container, so Docker alone is sufficient.

## Getting Started

### 1. Clone and Setup

```bash
git clone git@github.com:lucenia/lucenia-tutorials.git
cd lucenia-tutorials/13_parquet
source env.sh
```

### 2. Add Your License

Copy your Lucenia license into the config directory the container mounts:

```bash
mkdir -p node/config
cp ~/Downloads/trial.crt node/config/
```

### 3. Generate the Sample Parquet File

This writes `node/config/data/cars.parquet`, which the container sees at the
relative path `data/cars.parquet`:

```bash
./scripts/generate_data.sh
```

The file is the classic `mtcars` table (32 rows) plus a few columns chosen to
exercise every branch of Lucenia's schema inference (a boolean, a timestamp, and
a non-string binary column). See [The Data Model](#the-data-model) below.

### 4. Start the Cluster

The `docker-compose.yml` mounts `./node/config/data` into the node's config
directory so the Parquet file can be referenced with a simple relative path. Run
step 3 first so that directory already contains `cars.parquet`.

```bash
docker compose up -d
```

### 5. Verify the Cluster and the Parquet Module

```bash
curl -X GET https://localhost:9200/_cluster/health?pretty \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD

# The parquet module ships with the image — confirm it's loaded:
curl -X GET "https://localhost:9200/_cat/plugins?v" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD | grep -i parquet
# lucenia-node  parquet [module]  0.12.0
```

## The Data Model

`cars.parquet` is generated by [`generate_cars_parquet.py`](generate_cars_parquet.py).
Its columns are deliberately chosen so the mount response demonstrates each
inference rule:

| Column | Parquet type | Inferred Lucenia type | Demonstrates |
|--------|--------------|-----------------------|--------------|
| `model` | `BYTE_ARRAY` (String) | `keyword` | String → keyword; used as the `_id` |
| `mpg` | `DOUBLE` | `double` | Floating point |
| `cyl` | `INT32` | `integer` | 32-bit integer |
| `hp` | `INT32` | `integer` | 32-bit integer |
| `wt` | `DOUBLE` | `double` | Floating point |
| `gear` | `INT32` | `integer` | 32-bit integer |
| `am` | `BOOLEAN` | `boolean` | Boolean — in `_source` but not queryable on a mount |
| `last_serviced` | `INT64` (Timestamp ms) | **`long`** | Dates/timestamps map to epoch-millis `long`, **not** `date` |
| `raw_signature` | `BINARY` (no String) | *skipped* | Non-string binary isn't mapped (still in `_source` as base64) |

> **Compression:** Only the `UNCOMPRESSED` and `SNAPPY` Parquet codecs are
> supported. Files using `ZSTD`, `GZIP`, `LZ4`, `LZO`, or `BROTLI` are rejected at
> mount time with a `400`. The generator writes SNAPPY.

## Part 1 — Mount a Parquet File

Mounting validates the file, infers field mappings from the Parquet footer, and
creates a read-only index. No data is copied.

```bash
./scripts/mount_parquet.sh
```

### The mount request

`path` is required; `id_column` is optional (its values become each document's
`_id`; if omitted, the row index is used).

```bash
curl -X PUT "https://localhost:9200/_plugins/parquet/mtcars?pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD \
  -H 'Content-Type: application/json' \
  -d '{
  "path": "data/cars.parquet",
  "id_column": "model"
}'
```

### The mount response

The response reports the row count, the inferred queryable fields, and any
columns that were skipped:

```json
{
  "acknowledged": true,
  "index": "mtcars",
  "row_count": 32,
  "fields": {
    "am": "boolean",
    "cyl": "integer",
    "gear": "integer",
    "hp": "integer",
    "last_serviced": "long",
    "model": "keyword",
    "mpg": "double",
    "wt": "double"
  },
  "skipped_columns": [
    {
      "reason": "non-string binary columns are not mapped",
      "name": "raw_signature",
      "parquet_type": "BINARY"
    }
  ]
}
```

Notice `last_serviced` became `long` (epoch milliseconds), and `raw_signature`
was skipped because it's a non-string binary column — it's still returned in
`_source` (as a base64 string), just not queryable.

### How it works

The module maps a Parquet file to Lucene one-to-one:

- **one row → one document** (`_id` = the Parquet row index, unless you set
  `id_column`)
- **one column → one field**
- **one file → one segment → one shard**

Because the file *is* the segment, a mounted index is always single-shard and
read-only. The inferred mapping marks numeric fields `index: false` (queries run
on doc values) and keyword fields `doc_values: false` (queries run on postings):

```bash
curl -X GET "https://localhost:9200/mtcars/_mapping?pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD
```

## Part 2 — Query the Mounted Index

A mount answers `_search`, `_count`, and `GET`. Run the supported queries:

```bash
./scripts/query_parquet.sh
```

### Numeric range query

```bash
curl -X POST "https://localhost:9200/mtcars/_search?pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD \
  -H 'Content-Type: application/json' \
  -d '{ "query": { "range": { "mpg": { "gte": 31.0, "lte": 35.0 } } } }'
# → Fiat 128 (32.4), Toyota Corolla (33.9)
```

### Keyword term query

```bash
curl -X POST "https://localhost:9200/mtcars/_search?pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD \
  -H 'Content-Type: application/json' \
  -d '{ "query": { "term": { "model": "Valiant" } } }'
# → Valiant: hp 105, cyl 6
```

### Numeric aggregation

```bash
curl -X POST "https://localhost:9200/mtcars/_search?filter_path=aggregations&pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD \
  -H 'Content-Type: application/json' \
  -d '{ "size": 0, "aggs": {
        "avg_mpg": { "avg": { "field": "mpg" } },
        "max_hp":  { "max": { "field": "hp" } } } }'
# → avg_mpg.value = 20.090625, max_hp.value = 335.0
```

### Timestamps are `long`, not `date`

This is the most common gotcha. `last_serviced` is mapped as a `long` (epoch
**milliseconds**), not a `date` — the codec writes no Lucene points, and an
`index: false` `date` field would have no doc-values range path. So query it with
a **numeric** range over epoch-millis:

```bash
# 2026-10-01T00:00:00Z == 1790812800000
curl -X POST "https://localhost:9200/mtcars/_search?pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD \
  -H 'Content-Type: application/json' \
  -d '{ "query": { "range": { "last_serviced": { "gte": 1790812800000 } } } }'
# → 2 cars serviced on/after 2026-10-01: Maserati Bora, Volvo 142E
```

Passing a human-readable date string instead fails to parse against the `long`
field (`400 query_shard_exception: For input string: "2026-04-01"`), so always
convert dates to epoch milliseconds first.

### GET a document by `_id`

Because we mounted with `id_column: model`, each document's `_id` is the car's
name:

```bash
curl -X GET "https://localhost:9200/mtcars/_doc/Camaro%20Z28?pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD
# → found: mpg 13.3, hp 245, am false, ...
```

## Part 3 — Limitations of a Mount

The read-only view runs directly against the Parquet file, so some operations
aren't available until you promote it (Part 4). Each of these returns an error
(or empty result) — that's expected:

| Operation | Result on a mount | Why |
|-----------|-------------------|-----|
| Keyword **aggregation** (`terms` on `model`) | `400` — *"fielddata is unsupported on fields of type [keyword]"* | keyword fields have `doc_values: false` |
| **Sort** on a keyword field | `400` — same fielddata error | no doc values to sort on |
| **Boolean** column query (`term` on `am`) | `400` — *"Cannot search on field [am] since it is not indexed"* | boolean columns aren't queryable on a mount |
| Any **write** (`index`/`update`/`delete`/`_bulk`) | `400` — *"index [mtcars] is a read-only parquet-backed index"* | the Parquet file is the source of truth |

The `query_parquet.sh` script exercises all four so you can see the exact
responses. Numeric aggregations and sorting **do** work — only keyword
aggregation/sort and boolean queries are affected.

## Part 4 — Promote to a Regular Index with `_reindex`

To get the full query surface, copy the mounted rows into a normal index with the
standard `_reindex` API. The destination gets its own dynamic mapping and full
indexing (Lucene points, keyword field data, aggregations, sorting):

```bash
./scripts/promote_reindex.sh
```

```bash
curl -X POST "https://localhost:9200/_reindex?refresh=true&pretty" \
  -ku admin:$LUCENIA_INITIAL_ADMIN_PASSWORD \
  -H 'Content-Type: application/json' \
  -d '{
  "source": { "index": "mtcars" },
  "dest":   { "index": "mtcars_ingested" }
}'
```

After promotion, the operations that failed in Part 3 now work against
`mtcars_ingested`:

- **Keyword aggregation** — count cars by `gear` → `{3: 15, 4: 12, 5: 5}`
- **Sort** — three lightest by `wt` → Lotus Europa, Honda Civic, Toyota Corolla
- **Boolean query** — `term am=true` counts the 13 manual-transmission cars
- **`_id` preserved** — because the mount used `id_column: model`, `GET
  mtcars_ingested/_doc/Lotus%20Europa` still works

Once promoted, the mounted `mtcars` index can be safely deleted — **deleting a
mount never touches the underlying Parquet file.**

## Configuration & Path Sources

The `path` field accepts several forms:

| Path form | Example | Notes |
|-----------|---------|-------|
| Relative | `data/cars.parquet` | Resolved against the node config dir; **always allowed** (used in this tutorial) |
| Absolute local | `/srv/parquet/cars.parquet` | Must be under a `parquet.allowed_paths` entry; forces `number_of_replicas: 0` |
| `file://` URI | `file:///srv/parquet/cars.parquet` | Treated as a local file; same allowlist + replica rules |
| Hadoop / object store | `s3a://bucket/cars.parquet`, `hdfs://nn/cars.parquet` | Requires the relevant repository connector; reachable from all nodes, so replicas use the cluster default |

For absolute local paths, allow the directories in the node's `lucenia.yml`:

```yaml
parquet.allowed_paths: ["/srv/parquet"]
```

With Docker you can also supply this as a node setting via the container
environment (the same way `docker-compose.yml` already passes
`plugins.license.certificate_filepath`) rather than editing the YAML.

Any path resolving outside the node config directory or the allowed paths is
rejected — a guard against reading arbitrary files on the node.

## Data Type Mapping Reference

| Parquet column | Mapped type | Notes |
|---|---|---|
| `INT32` | `integer` | Range/term/aggregations run on doc values |
| `INT64` | `long` | |
| `FLOAT` | `float` | |
| `DOUBLE` | `double` | |
| `INT32`/`INT64` + `DECIMAL` | `double` | Decoded with the column's scale |
| `INT32` + `DATE` | `long` | Epoch **days** stored as a number, not `date` |
| `INT32`/`INT64` + `TIMESTAMP` | `long` | Epoch milliseconds; micro/nanos truncated to millis |
| `BINARY` (UTF-8 String) | `keyword` | Term/match on postings; no aggregations/sort |
| `BOOLEAN` | `boolean` | In `_source`; not directly queryable until reindex |
| Nested / repeated / non-string binary / `INT96` / `FIXED_LEN_BYTE_ARRAY` | *skipped* | Not queryable; still emitted into `_source` |

## Key Takeaways

- **Mounting** a Parquet file gives you an instant, read-only, single-shard index
  you can search *in place* — no ingest, no copy.
- The schema is **inferred** from the Parquet footer; numeric and keyword columns
  are queryable, while boolean and non-string-binary columns are preserved in
  `_source` but not directly queryable.
- **Dates/timestamps become `long` epoch-millis** — query them with numeric
  ranges, not date ranges.
- The mount's query surface is intentionally narrow. **Promote with `_reindex`**
  to get sorting, keyword aggregations, and writes.
- Only `SNAPPY`/`UNCOMPRESSED` Parquet files are supported, and this feature is
  **experimental** — great for inspection and cold-data queries, not production.
